# CONTRIBUTING — 本仓库协作规则

> **生效日期**：2026-11-08　**版本**：v1.0　**存放位置**：`docs/CONTRIBUTING.md`
> 本文件即本仓库的协作规则正文（按约定存放于 `docs/` 目录）；仓库根目录的 `CONTRIBUTING.md` 仅为指向本文件的入口，请勿在根目录文件中直接修改规则。
> **修订方式**：对本文件的任何修订本身也必须遵守本规则——以 `docs:` 类提交经 `git push` 生效，修订历史即规则变更历史。

---

## 一、适用范围

- 适用于所有向本仓库提交代码或文档的协作者，**包括人类成员与 AI 助手 / 自动化代理**。
- 核心思想：**GitHub 是唯一真相源**。对话窗口与本地沙箱均为易失工作区——沙箱回收或回退后，内存态全部丢失、未推送的本地状态可能回滚；任何有价值的产出必须落库（commit + push），任何"唯一副本"不得只存在于对话记录或本地文件中。

## 二、协作规则（核心七条）

| # | 规则 | 一句话要点 |
|---|------|------------|
| 1 | 唯一同步方式 | 改动一律 commit + push，不在对话中凭空产生代码 |
| 2 | 仓库位置 | 全库仅一个仓库路径，不在其他目录创建 `.git` |
| 3 | 提交规范 | 小步提交 + Conventional Commits 风格 |
| 4 | 会话记录 | 分析/评估/测试记录写入 `docs/` 并推送 |
| 5 | 禁止 force push | 含对已推送 commit 的 amend 后推送（等效 force） |
| 6 | Rebase 前置 | 先评估 revert/merge 替代方案，必要时提前确认 |
| 7 | bug 修复不重命名变量 | 重命名只发生在 refactor 提交中 |

### 规则 1 ｜ 唯一同步方式

**所有代码/文档改动通过 `git commit` + `git push` 推送到 GitHub，不在对话中凭空产生代码。**

- 对话中的代码片段、方案讨论仅是草稿；任何被采纳的"最终版本"必须落入仓库并推送。
- 判定标准：一项改动是否"已存在"，以它是否出现在 GitHub 仓库为准，而不是以它是否出现在聊天记录里为准。
- 例外：纯本地试算、无保留价值的一次性实验可不提交；一旦需要被引用或复用，即受本条约束。

### 规则 2 ｜ 仓库位置

**仓库根目录：`/home/z/my-project/`。不在其他目录创建 `.git`（全库仅以本路径为准）。**

- 本条路径由仓库所有者根据实际环境确认填入；若仓库迁移或更换环境，必须先修订本条，再迁移目录。
- 任何子目录、临时目录或克隆副本中创建第二个 `.git` 均属违规——嵌套仓库与游离副本会导致改动失联、真相源分裂。

### 规则 3 ｜ 提交规范

**小步提交，commit message 使用 Conventional Commits 风格（`feat:` / `fix:` / `docs:` / `refactor:` / `chore:` / `test:`）。**

- 格式：`类型(可选范围): 简短描述`，一行以内、祈使句、不加句号。
- 示例：
  - `feat(edit): 支持最多 10 张参考图合成`
  - `fix(vae): 修复 RGBA 透明边缘伪影`
  - `docs: 新增仓库协作规则`
  - `test: 补充图像编辑流水线冒烟测试`
  - `chore(deps): 升级 diffusers 至源码版`
  - `refactor: 抽取图像预处理公共函数`
- "小步"参考标准：一次 commit 对应一个完整、自洽、可验证的改动单元；修复与重构分开提交（与规则 7 呼应）。
- 反例：`update`、`fix bug`、`修改一些文件`（无类型、无信息量）。

### 规则 4 ｜ 会话记录

**分析/评估/测试记录写入 `docs/` 目录，以 Markdown 形式提交推送。**

- 命名建议：`docs/notes-<YYYYMMDD>-<主题>.md`，例如 `docs/notes-20261108-显存实测.md`。
- 会话中得出的结论、基准数据、踩坑记录，凡具有保留价值的，一律落盘到 `docs/` 并推送——聊天记录不是存档介质。

### 规则 5 ｜ 禁止 force push

**绝不使用 `git push --force`；同理禁止对已推送 commit 执行 `--amend` 后再推送（等效 force，同样触犯本条）；未推送 commit 的 amend 属修正笔误的常规手段，不受限。**

| 情形 | 是否允许 |
|------|----------|
| 对未推送的本地 commit 执行 `--amend` | ✅ 允许（修正笔误的常规手段） |
| 对已推送的 commit 执行 `--amend` 后再 push | ❌ 禁止（等效 force） |
| `git push --force` | ❌ 禁止 |
| `git push --force-with-lease` | ❌ 禁止（任何形式的远端历史改写均视为 force） |

- push 被拒（non-fast-forward）时的正确路径：先 `git fetch`，按规则 6 评估 rebase 或 merge，而不是 force。
- 若确有覆盖远端的极端需求（如误推送了敏感信息），必须先在会话中向仓库所有者说明并获得确认后处理，处理方式优先选择在 GitHub 端操作（如吊销凭证）而非改写历史。

### 规则 6 ｜ Rebase 前置

**rebase 前先评估替代方案（revert / merge），必要时提前告知确认。**

- 决策参考：
  - 撤销**已推送**的错误提交 → 首选 `git revert`（生成反向提交，不改写历史）；
  - 个人分支落后主分支、且该分支未与他人共享 → 本地 rebase 可自行执行；
  - 涉及改写已推送历史（interactive rebase、drop/reset 已推送 commit）→ **必须提前告知并获得仓库所有者确认**，且即使获得确认，也仅限操作个人分支（与规则 5 联动）。
- 不确定时，默认选择 merge 或 revert，并说明理由。

### 规则 7 ｜ bug 修复不重命名变量

**修复 bug 时保持原变量名，仅在 refactor 时重命名。**

- 原因：修复 commit 的 diff 越小，评审越快、责任越清晰、`git blame` 越可读；修复中混入重命名会淹没真正的逻辑变更。
- 执行方式：修复提交只做最小必要改动；确有重命名需求，另开独立的 `refactor:` 提交——先修 bug、后重构，两次提交两个目的。
- 边界情况：若修复本身必须改动变量的作用域或类型，保持名字不变、只改必要部分；命名优化留给后续 refactor 提交。

## 三、常见场景速查

| 场景 | 正确动作 | 禁止动作 |
|------|----------|----------|
| 在对话中讨论出一段代码 | 落盘为文件 → commit → push（规则 1） | 让代码只存在于聊天记录 |
| 写 commit message | `类型(范围): 描述`（规则 3） | `update` / `fix bug` 等无类型消息 |
| push 被拒 | fetch → 按规则 6 评估 rebase/merge | `--force`（规则 5） |
| 已推送的 commit 有错 | `git revert`（规则 6） | amend 后再 push（规则 5） |
| 本地未推送的 commit 写错 | `git commit --amend` | ——（不受限） |
| 修 bug 时想顺手改名 | 保持原名，另开 `refactor:` 提交（规则 7） | 修复提交里夹带重命名 |
| 做了一轮测试/评估 | 写入 `docs/notes-*.md` 并推送（规则 4） | 结果只报在对话里 |
| 想在别的目录建库实验 | 只在规则 2 指定路径内工作 | 其他目录创建 `.git`（规则 2） |

## 四、违规处理

- **违反规则 5**（任何形式的 force push / 已推送 amend）：立即停止操作，在会话中报告仓库所有者，评估是否需要补救（revert 或恢复）。
- **其余违规**：在下一次提交前自行修正（补提交、补文档），并在 commit message 中注明。

## 附：安全基线提醒（通用工程约定，非新增规则）

- 任何 Token / 密钥 / 密码**不入仓库**（包括提交历史）：凭证只存在于 GitHub Secrets 或本地 `.env`，且 `.env` 已被 `.gitignore` 排除、不纳入版本控制。
- 一旦怀疑凭证泄漏：立即在 GitHub 端**吊销并轮换**（服务端吊销对本地状态回退免疫），而非删除文件了事。
- 本地 `.env` 仅视为可丢弃缓存；仓库内可保留 `!.env.example` 模板（只含变量名，不含值）。
