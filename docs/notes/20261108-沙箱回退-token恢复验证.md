## 2. 验证方法

**静态检查（持久层完整性）**：确认所有关键状态均已落盘于 `/home/z/my-project/`（该路径在沙箱回收/回退中持久保留），且无任何凭证进入版本控制。

**动态冷启动测试（模拟回退后状态）**：
```bash
env -i PATH=/usr/bin:/bin HOME=/home/z \
    GIT_TERMINAL_PROMPT=0 \
    GIT_ASKPASS=/home/z/my-project/scripts/git-askpass.sh \
    git -c credential.helper= -C /home/z/my-project ls-remote --heads origin
```
要点：`env -i` 清空全部继承环境变量（等效回退后内存/进程态归零）；`-c credential.helper=` 清空凭证 helper；`GIT_TERMINAL_PROMPT=0` 禁止终端交互——**认证只允许经由 askpass 脚本从 `.env` 读取 token 这一条路径完成**。

## 4. 边界说明（诚实声明）

1. **本验证无法从沙箱内部触发"真实回退事件"**：已验证的是回退后恢复机制的**全部前置条件落盘持久** + **冷路径认证可用**。终极实测方法：下次全新会话中不提供任何 token、不做任何配置，直接执行 `git push`——成功即为全链路实测通过。
2. **若未来冷启动测试中认证被拒**：属预期安全行为——说明 token 已在 GitHub 端被吊销（L1 服务端裁决），机制本身完好；重新提供新 token 写入 `.env` 即恢复（幂等操作，脚本无需改动）。
3. **文件级回退的残余风险**：若回退快照早于 token 写入时点，`.env` 中的 token 会丢失——恢复方式同上（重新写入即可），属"可丢弃缓存"设计的正常代价，不构成机制失效。
4. askpass 脚本与 `.env` 同在 `scripts/`、项目根目录下（均被 gitignore 排除），与代码同生命周期落盘持久。

## 5. 关联机制回顾

- L1–L3 状态全部在 GitHub 服务端，天然免疫本地回退；
- L4 遵循"**唯一副本永不落沙箱、本地仅存可丢弃缓存**"原则；
- 服务端吊销（L1）对本地任何状态（包括回退复活的旧 token）具有最终否决权——fail-safe 而非 fail-silent。
